Lookback: Claude Code / Codex のログを検索可能な長期記憶にする

2026-07-09·2 分

Claude Code や Codex を日常的に使っていると、開発中の判断、試行錯誤、失敗した方針、あとで見返したい会話などが自然にセッションログへ蓄積されていく。これはかなり価値のある記録だと思っている。一方で、実際には時間が経つほどログは大量になり、人間が直接読むものではなくなっていく。

Claude Code や Codex 自体も過去セッションを検索して回答してくれることはある。ただ、過去ログ全体を grep したり読み直したりする作業はそれなりにトークンを消費するし、毎回その場で掘り返すには重い。自分としては、過去のセッションログから知識を取り出して、検索・要約・再利用できる形にしたいという気持ちが強かった。

そこで作っているのが Lookback というデスクトップアプリである。

Lookback

https://github.com/jobworkerp-rs/Lookback

何を解決したかったか #

たとえば、過去に同じような設計で迷っていなかったか、ある実装方針をなぜ採用しなかったのか、レビューで何度も指摘されている癖はないか、といった情報は、単なるログとして残っていてもなかなか活用しづらい。検索でき、要約され、必要ならチャットから質問できる形になっている方が使いやすい。

Lookback という名前は、過去の知識を思い出して振り返るための道具、というところから付けている。

おまけ #

最近は、エージェントにかなり広い範囲の作業を任せて、自律的に動かす方向の話題が増えている。判断も含めて全自動に寄せる方向はそのままでは少し自分には合わない感覚がある。 動作などの判断の主体はできるだけ自分側に残しておきたい。

ただ、その流れの中で重要だと思ったものもある。エージェントが実行時に過去の情報を参照し、ユーザの傾向や反省点を更新していく仕組みである。これはエージェントだけが内部的に使うのではなく、人間も見られる形にしておくと有益なのではないかと考えた。(必要に応じてプロンプトで指定したりするのに役立つイメージ) 直接使えるものになるかは分からないが試みとして抽出して閲覧できるようにしている。

Lookback でできること #

Lookback は、ローカルに残っている Claude Code / Codex のセッションログを取り込み、検索可能な長期記憶として扱うための Tauri デスクトップアプリである。現在は主に以下のことができる。

  • ~/.codex/sessions や ~/.claude/projects にあるセッションログをインポートする(1セッションを1メッセージスレッドとして扱う)
  • .md / .txt のプレーンテキストをスレッドとしてインポートする
  • インポート済みスレッドをキーワード検索、セマンティック検索、ハイブリッド検索、ラベル検索で探す
  • スレッド単位、日次、週次、月次の要約を生成する
  • 各セッションから reflection、つまり反省点や改善観点を抽出する
  • 過去セッションからユーザーの personality profile を生成する
  • RAG チャットで、過去のログや要約に対して質問する
  • MCP サーバとしてローカルホストで公開(lookback_recall)し、各種MCP クライアントから検索する
  • 定期インポートや定期要約をスケジュールする

ラベル検索では、Codex / Claude Code のような利用元、実行ディレクトリ名、ブランチ名、ファイルパス名などで絞り込める。

画面としては、スレッド、要約、自省、personality、チャットの各タブから目的の情報を見られるようにしている。

検索結果を自分で1件ずつ吟味するのが面倒なときは、チャットタブから質問できる。RAG チャットは生成済みの要約と元のメッセージの両方を検索し、回答内のソースリンクから該当スレッドや要約へ戻れるようにしている。

また、検索機能は MCP サーバとして外部にも出せるようにしている。Claude Code と Codex の両方を使っている場合、それぞれのログを横断して検索できると便利な場面がある。「どちらのツールで話した内容だったか」を人間が思い出す負担は下げられるのではないかと思っている。 (検索精度についてはまだ評価しきれていない部分はある)

ローカル LLM で完結できる #

Lookback の特徴の1つは、ローカル LLM で完結できる構成にしていることである。

セッションログには、開発中の詳細な文脈や、まだ公開していないコード・設計・判断が含まれることが多い。これを常に外部 API に送るのは、用途によっては抵抗がある。もちろん外部 LLM を使える選択肢は必要だが、トークンコストも考えるとローカルだけで動かせるようにもしておきたかった。

現在は、ローカル LLM 実行には llama.cpp ベースの runner を使っている。外部 LLM も rust-genaiを利用してOpenAI 互換 API 経由などで利用できるようにしている

一方で、embedding 処理は現時点ではローカルモデル利用に限定している。ここは必要があればリモートの embedding API も選べるようにするかもしれないが、まずはローカルでセッションログをベクトル化し、検索できる状態を作ることを優先している。

ただし、ローカル LLM の実行はかなり重い。モデルやメモリ容量によっては、普段の作業と同時に走らせると邪魔になることがある。そのため、Lookback には定期実行機能も入れている。常時起動している環境であれば、寝ている時間などにインポートや要約を実行するのが現実的だと思う。

技術構成 #

技術的には、Lookback は Tauri v2 + React + TypeScript のデスクトップアプリで、バックエンド側に Rust の sidecar プロセス群を起動する構成になっている。

検索・記憶ストアには memory-store を利用している。memory-store 側では LanceDB を使い、BM25 と vector search を組み合わせたハイブリッド検索を行えるようにしている。

重い処理は jobworkerp に載せている。embedding 生成、LLM 実行、要約、reflection、personality 生成などはキューイングして非同期ジョブとして実行される。ワークフローの管理には jobworkerp-conductor も使っており、定期実行や複数ステップの処理を workflow として扱っている。

ローカル LLM 実行には、llama.cpp の Rust wrapper である llama-cpp-rs を使った llama-cpp-runner を作成して利用している。 外部 LLM 実行には rust-genai を利用しており、この crate が対応している外部 LLM については実行できる見込みである。 (LiteLLM などのopenai互換APIを使った別モデル利用の場合にはモデル名の先頭に openai:: を付ける形式になる) embedding については fastembed を使った mm-embedding-runner を利用している。

大まかには、以下のような構成である。

graph TB App[Lookback UI<br>Tauri + React] --> Memory[memory-store<br>threads / summaries / search] App --> Jobworkerp[jobworkerp sidecar] Memory -- embedding jobs --> Jobworkerp Conductor[jobworkerp-conductor<br>workflow / periodic tasks] --> Jobworkerp Jobworkerp --> LlmRunner[llama-cpp-runner<br>local LLM] Jobworkerp --> EmbeddingRunner[mm-embedding-runner<br>embedding] Memory --> LanceDB[(LanceDB<br>BM25 + vector search)] Jobworkerp --> Mcp[MCP server<br>lookback_recall]

この構成にしているのは、ログのインポート、embedding、要約、チャット、定期実行がそれぞれ重くなりやすいからである。UI プロセスに全部を抱え込むより、ジョブとして分離し、必要な処理を sidecar 側で流した方が扱いやすい。

また、自分が以前から作っている jobworkerp-rs を活用したローカルアプリケーションの例として意味のあるものになったと感じている。ジョブワーカー基盤、workflow、Function(LLM runner、embedding runner)、データストア(検索含む)を組み合わせると、AI アプリケーションの裏側で必要になる処理をそれなりに自然に表現できたと感じている。

使いどころ #

Lookback は、エージェントを自律動作させるためというより、自分の過去の作業履歴を再利用しやすくするための道具として作っている。

たとえば、以下のような使い方を想定している。

  • 以前検討した設計方針を探す
  • 特定のバグや実装方針について、どのセッションで話したかを検索する
  • 日次・週次の作業要約を生成して、自分の作業ログとして読む
  • reflection を見て、繰り返している失敗や改善点を確認する
  • personality profile を見て、AI が推測した自分の作業傾向を点検する
  • Claude Code や Codex から MCP 経由で過去ログ (要約と実セッションログ) を検索して過去の知識を踏まえた実装計画を実現する

特に reflection や personality は、出力が常に正しいというより、外部化された観察として見るのがよいと思っている。AI が推測した自分の傾向をそのまま信じる必要はないが、見返すことで「確かにこれは気をつけた方がいいかもしれない」と気づくことはある。

今後やりたいこと #

今後は画像の import に対応し、画像検索もできるようにしたいと考えている。現在の主対象はテキストログだが、開発中のスクリーンショットやUIの状態、設計メモの画像なども記憶として扱えると便利そうである。

また、検索精度や要約品質についてはまだ改善の余地が大きい。特に、どの粒度でスレッドを要約するのがよいか、reflection をどのように整理すると後から役に立つか、MCP 経由でエージェントにどこまで使わせるのがよいかは、実際に使いながら調整していくつもりである。

ログは溜まるだけではすぐに使えなくなる。Lookback は、そのログを検索できる記憶として扱い、自分自身が過去の判断や作業を振り返れるようにするための試みとなる。
