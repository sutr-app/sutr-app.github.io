1では、Rust製ジョブワーカーシステム jobworkerp-rs の開発動機と、gRPCを利用した準同期的な結果返却を実現するシステムについて記載した。 本稿では、内部のストレージや、多様な処理をさばくためのワーカー実装について解説したい。

1. 用途に応じたストレージ構成とスケール設定 #

ジョブのライフサイクルを管理するストレージ層は、用途に応じた選択肢を提供し、ハイブリッドに動作するよう設計してみた。システム起動時の環境変数（STORAGE_TYPE）によって構成の切り替えが可能になっている。

Standalone（シングルインスタンス）構成 #

複数台へスケールさせる要件のない小規模運用や、ローカル開発環境に向けた構成である。 RedisやMySQLのセットアップは不要であり、内部の Memory Channel (mpsc/broadcast channel) と SQLite で動作する。単独で迅速に起動でき、検証用途などで手軽に扱える。またリアルタイム処理が必要な場合にメモリベースで遅延が少なく処理ができる。

Scalable（スケーラブル）構成 #

高可用性が要求されるシステムを想定し、Redis + RDB (MySQL) の構成も用意した。 即時実行ジョブはRedisの機能（BLPOPなど）を用いて即座に処理を開始し、時刻指定ジョブや長期のリトライが必要なジョブはMySQL等のRDBで管理させている。

ジョブをRDBに永続化しつつ、同時にRedisへキューイングするモード(WithBackup)も実装している。 これを使うとジョブ実行中にワーカーのクラッシュやフリーズが発生したとしても、再起動時にRDB側に残存するタイムアウト済みジョブを再取得し、自動または手動でRedisやメモリへ復帰させて再実行できる仕様になっている。(RDB書き込みのオーバーヘッドはある)

2. リソースを効率化する実装 #

チャネルごとの並列度制御と実行プール #

ワーカーでは、実行チャネル (名前付きの実行キューの単位) に対して柔軟なリソースの割り当て制御ができるようにした。 例えば、GPUを占有するLLM推論タスクのチャネルは並列度1、IOバウンドで並列処理可能な汎用タスクチャネルは並列度8といった制約が環境やタスクに応じて設定できる。ワーカーサーバごとに設定でチャネルを割り当てることで実行する機能をサーバごとに割り振ることができる。

ワーカーインスタンス(ホスト単位ではなくプロセス内部のクラスインスタンスの話)の初期化コスト（パッケージやモデルのロード等）は非常に重いこともあるためワーカーインスタンスを再利用する機構を導入した。 ワーカー生成時に use_static オプションを指定することで、特定の設定で初期化を終えたワーカーを、チャネルの並列度に合わせてメモリ上にプールする。ジョブ実行時は引数を引き渡すだけになるため、メモリ消費は大きくなるが初期化オーバーヘッドは低減できる。

同期・非同期・ストリーミングによる結果取得方式 #

ジョブの実行結果（レスポンス）の取得方式は以下の2種類から選択できるようにした。

  • NO_RESULT: 結果の完了を待機せずにレスポンスを返し、完全に非同期で処理を行うタスクに用いる。下記broadcast_results設定をすることで必要なクライアントがListenリクエストしてレスポンスを取得することは可能である。
  • DIRECT: 実行結果を同期的に取得する方式である。RedisのPub/Sub機能を利用し、ワーカーから処理完了の通知が到達するまでアイドル状態で待機し、結果をダイレクトに返却する。

加えて broadcast_resultsを有効にするとジョブの実行結果をリアルタイムでListenしている複数クライアントにStreaming配信する機能を有効にできる。ジョブの登録者と購読者を別で用意できる (が、接続可能なユーザに対しては誰でも結果を見られることにはなる)。

3. ワーカーの汎用化とワークフロー定義 #

ジョブワーカーのワーカー内部のロジックを使用言語固有のコードで実装する必要があることもあるが、そこまで頑張る必要がないこともわりとある。そこで本システムでは、よく使いそうな定型的な処理をあらかじめ「組み込みランナー」として用意する方針をとった。

  • 組み込みランナー: Shellコマンド実行(COMMAND)、HTTPリクエスト、gRPC unary, streaming（リフレクションベース）、Dockerコンテナ実行、Pythonスクリプト実行、LLM呼び出し（Ollama, 外部API等）、Workflow(後述)。
  • 拡張機能: Rustのdylibによる動的ロードを利用したプラグイン拡張や、MCP（Model Context Protocol）に準拠したサーバーへの拡張もできるようにしている。外部のMCP server (stdio, sse) をrunnerとして登録・実行できる。

Serverless Workflowによる処理の抽象化 #

ちょっとした処理を連携させるためだけに、rustコードを書くのはコストが高いと感じていた。つまり rustで記載してしまうとロジックを少し修正するたびに再ビルドが必要になり面倒が多いし可読性もあまりよくない。 ジョブの「順次実行」「条件分岐 (if, switch)」「繰り返し (for)」「入出力変数のマッピング」等を扱えるシンプルなワークフローを実行できると便利だと考えて調べたところ、Serverless Workflow の仕様がシンプルで扱いやすそうだった。仕様全体までは必要なかった(実装するのが大変)ためシンプルなロジック構築の部分を抜きだして実装している。(実装範囲はスキーマに定義してある範囲になる) runタスクは準同期ジョブとして各チャネルで(scalableな場合は分散)実行される。システム既存の待機機構（Pub/Sub）を用いて前段の処理完了を待ち受け、次ステップへ結果を渡せる作りにしている。 またチェックポイント機能でワークフロー途中で中断・再開させることもできる。HITLのような仕組みはチェックポイントを利用して中断することで実現するような想定をしている。

4. フロントエンド機能 #

ここまではジョブワーカーの内部構造の話だったが、作ったランナー、ワーカーやワークフローを実際に使うには、外部のクライアントやAIエージェントから叩けるようにする入り口が要る。gRPCのクライアントを書くのは手間なので、既存の互換APIやUIとしてのフロントエンド実装をいくつか用意してみた。どれもまだ実験的な実装になる。

MCPサーバープロキシ機能 #

一つ目は、jobworkerpの機能を MCP (Model Context Protocol) のツールとして公開する機能である。(mcp-server/README_ja.md)

先述の「外部のMCP serverをrunnerとして取り込む」プロキシとは逆方向で、こちらは jobworkerp自体をMCPサーバーとして見せる ものになる。登録済みの組み込みランナー（COMMAND, HTTP_REQUEST, LLM, WORKFLOW 等）や、plugin、mcp server runner等で組み込んだWorkerを、そのままMCP serverのツールとして列挙・実行できる。Codex、Claude codeなどのクライアントの設定ファイルにmcp serverとして登録することで自分で組んだワークフローなどの機能を各種クライアントのLLMから利用可能になる。 (Runnerツールは初期化設定と呼び出し引数の両方が要るので引数のjsonは { "settings": {...}, "arguments": {...} } の形、Worker側は設定が生成時に固定済みなので arguments をそのまま渡せるので登録したworkerを登録してmcp利用することをお勧めする)

トランスポートは mcp-http と mcp-stdio の二種類がある。 FunctionSetを定義することでMCP serverとして利用するworker, runnerを制限して定義、切り替えることができる。

AG-UIフロントエンド #

二つ目は、AG-UIプロトコル に準拠したHTTP SSEサーバ:ag-ui-front/README_ja.md

これは「ワークフローの実行過程をリアルタイムにUIへ流す」機能になる。ワークフローの実行を開始すると、SSE (Server-Sent Events) で RUN_STARTED / STEP_STARTED といったライフサイクルイベントや、LLMのストリーミング出力（TEXT_MESSAGE_CONTENT）、ツール呼び出しの経過などが逐次配信される。チャットUIのような、途中経過を見せたいフロントエンドを繋ぎこむことを想定している。

チェックポイント機能を活用したHITL (Human-in-the-Loop)をできるようにしてみている。つまりワークフロー側で checkpoint: true を指定したタスク、LLMランナーで isAutoCalling: false としたツール呼び出しのタイミングで実行を中断し、ユーザーの承認や入力を待ち受けられる。

管理UI (Admin UI) #

三つ目は、システムの運用まわりのWeb管理ダッシュボード(React + Vite)である。(admin-ui) gRPCのAPIを gRPC-Web 経由で叩く構成にしてある。

WorkerやRunnerの作成・編集のほか、ジョブの投入（Protobufスキーマから動的にフォームを生成して実行）、実行結果の確認（Protobufをデコードして表示）、滞留したジョブの検出、RDBバックアップからRedisキューへのリストア、古いジョブ状態のクリーンアップといった、CLIやgRPCクライアントだと少し面倒な運用操作をGUIから行えるようにした。

フロントエンド機能はいずれもalpha段階の機能で、APIや挙動は予告なく変わりうる

5. おわりに #

Rustで何か作ってみたいというところから個人的にそこそこ使えそうなジョブワーカー、ワークフローシステムが作成できたような気がしている。 CPUやメモリを大量に消費するバッチ処理モジュールとして、また即時性が求められるパイプライン処理としてなど、色々な使い方ができそうなものとして作成できたと考えている。 (個人的には処理の外部ホストへのルーティングが可能なワークフローシステムとして自宅k8sでのサーバサイド処理をまかせている。また単独アプリのバックエンドとしても利用をしはじめている)

上で触れたMCPプロキシやAG-UI、管理UIまわりはまだ詰めきれていない実験的な実装なので、使い込んでいく中でこなれてきたら、それぞれについて改めて書いてみたい。
