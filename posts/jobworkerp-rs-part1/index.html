Rustでジョブワーカーシステムを作っている(1)

2026-03-31·1 分
目次

2021年頃からRustの学習をしたいと考え始めていた。直近まではScala等の抽象度の高い言語を主に使用していたが、個人的には、メモリ管理が厳密でローレイヤーな記述も可能なモダンな言語を学びたいという動機があった。C++は書いたことがあったが今最新のC++を学びなおすよりはrustを学ぶ方が色々実になりそうという気持ちだった。

学習の題材として利用経験もあり、設計・実装した経験もあった「ジョブワーカーシステム」にしようと考えた。(perlやjava、goでの経験) 2022年頃にはDeepLearningも成熟してきており、LLM等の技術が実用的になり始めているように感じていた。CPUヘビーでメモリ管理が重要となる処理や、リソースを大きく消費するタスクを非同期で効率的に処理する基盤として、ジョブワーカーはRustの実装対象として適しているのではないかと考えたからだ。(ジョブ実行ロジックがrust化したくなるものだったわけだが…) またtokio 1.0が2020年末にリリースされており、非同期処理が安定して使えるようになっているのではないかという期待もあった。

当初は素朴なジョブワーカーとして実装を始めたが、設計を進める中で自分なりに考えた「欲しい要件」に合わせてアーキテクチャを拡張していった。本稿では、開発したジョブワーカーシステム「jobworkerp-rs」の設計とアーキテクチャについて紹介する。

[https://github.com/jobworkerp-rs/jobworkerp-rs:embed:cite]

1. 最初に #

ジョブワーカーのアプローチとして「データベースに保存（エンキュー）して定期的にフェッチする」という素朴で確実なアプローチがあった。それでは処理が遅いということで、Redis等を利用して「リアルタイムなバッチ・キュー処理」(処理するサーバのみ外に出して結果は同期的に取得)が必要になることがあると感じていた。

大量のデータをさばく用途であればKafkaなどが適しているだろうが、そういう大規模ストリーミング処理用途ではなく、CPU負荷やI/O負荷が高く、時間のかかる処理に特化して、それらを効率的に(非・準)同期実行するworker基盤を作りたかった。つまりそこそこ疎結合にシステムを組めるがそれなりに処理も含めてまとめて面倒見れるまとまったシステムくらいの方が小・中規模くらいまでであれば使いやすそうと考えてジョブキューと処理をまとめたシステムになっている。

2. #

以下の要素を組み合わせたハイブリッドなアーキテクチャを採用することにした。

  • 永続性を重視するアプローチ（RDB）: 実行を急がなくていいタスク、時刻指定ジョブ、永続化やバックアップが必要なタスク
  • リアルタイム性を重視するアプローチ（Redis/メモリ）: 即座に実行し、レスポンスを早期に返却すべきタスク。(RDBバックアップを取れるオプションで永続性もサポート)

Rustに mpsc channel というキューを実現するのに適したメモリ構造がある。それを含めて活用し、両者の長所を用途に合わせて使い分けできるようなシステム基盤を検討した。

3. #

リアルタイム性、ストリーミングが簡単ということで、フロントエンドの通信プロトコルには gRPC/gRPC-Web (tonic)を利用している。

  1. ストリーミングのサポート: CPUやI/Oヘビーな処理の実行状況・結果をリアルタイムに返す際、ストリーミングレスポンスが返せる
  2. 型安全とバイナリ転送: 音声や画像などのバイナリデータを効率的に送受信できる。また、ジョブの引数やワーカーのスキーマ定義をProtocol Buffers（protobuf）で統一することで、効率的かつ型安全なシステムが構築しやすい(が、デバッグは面倒ではある)

（補足：gRPCのリクエスト構築が面倒に感じる場面もあるため、リフレクションを利用して手軽に実行できるclientやgRPC Web UIを実装している）

4. システム構成 #

システム構成は以下のようになっている。

graph TB Client[Client] --gRPC/gRPC-Web--> Frontend[gRPC Frontend] Frontend --Job registration--> Storage[(Storage layer)] Storage --Job retrieval--> Worker[Worker] Worker --Result storage--> Storage Frontend --Result retrieval--> Storage subgraph "Storage layer" Redis[(Redis/mpsc chan<br>Immediate jobs)] RDB[(RDB<br>MySQL/SQLite<br>Periodic/Scheduled/Backup jobs)] end Storage --- Redis Storage --- RDB subgraph "Worker processing" Worker --> Runner1[Runner<br>COMMAND / HTTP] Worker --> Runner2[Runner<br>Docker / LLM] Worker --> Runner3[Serverless Workflow] Worker --> RunnerP[Plugin Runner<br>Custom extensions] end

ジョブはストレージ層（メモリ/Redis/RDB）に登録され、ワーカーがそれをフェッチまたは購読(blpopなど)して実行する。システム全体をPub/Subベースの設計としており、実行結果は再びストレージ層やPub/Subを経由して即座にフロントエンドへ返せるような作りになっている。

今回はjobworkerp-rs の開発動機とハイブリッド構成を採用した全体構成についてまとめた。 次回はより具体的な構成、実行機構、組み込みランナーやWorkflowについて書く。
