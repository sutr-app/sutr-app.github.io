ライフタイムやcopy trait制約でのエラーに悩む

2022-03-09·1 分
目次

下記のようなエラーがでるとき

error: future cannot be sent between threads safely
  --> [code]
note: future is not `Send` as this value is used across an await
  --> [code]

asyncやfutureの中身にSendを満たしていないものがある。 asyncブロックやasync closureをつかっているときにまれによくある。 今回は where Self: Send とかasync closureの返り値のFutureをgenericsにして+Send や +Syncをつけたりして回避できた(まぁだいたいコンパイラが教えてはくれるが慣れるまで結構面倒)。 (うまくgenerics化しないと狙った箇所にマークできないことがある)

grpcのクラス自動生成したものにはライフタイムが付いていないが自分で作成したものには付けないと怒られる場合に最終的に自動生成したものとの齟齬ができてしまってビルドできなくなるというワナがある。何とか付けないで済むようにしていくとstaticが増えていき、selfにstaticを付ける必要がでてくるとまた自動生成のコードとの齟齬が発生してビルドできない。 なんとか付けなくて済むようにしようとしているが無理かもなぁ…

rustをscalaみたいにメソッドチェーン的に書こうとするとスコープに入って寿命が切れたりしてcopyが必要になったりするので、今の実力ではひたすらmatchでやっていくのが無難という感じになっている (if letでもpartial moveとかで部分的なコピーが必要になる)。どういうことかというと、structにStringのメンバとかが含まれているとcopyが必要になったタイミングでエラーになってしまう。Stringのcopyでエラーになるときの回避方法としては自分でclone()を明示的にかくといいのだが、細かくclone()を書いていこうとするとメソッドチェーンとかではなくmatchで細分してからのclone()で書くという形しか今は思いついていない(crateのerror型とかCloneとかCopyとかついてないもの多すぎて…))。自分が慣れてないだけでもっといい書き方あるんじゃないだろうか。。。(←たぶんArcなどで参照(ポインタ的なもの)として管理すればなんとかなりそう？)

(structをメモリキャッシュに積む、とかのケースでcopyするときにチェックにひっかかり、直すためにかなり煩雑なコードにしないと上手くいかなかったので自分がまだ上手い書き方を知らないだけなんじゃないかと思っている)

とにかく何でもいいから動くようにしてから考えよう。。。 (まだ動いていない)

追記 #

非同期 (async fnとか) で書いている場合は引数でわたす変数としてもArc(非同期対応の参照カウンタ式値参照)を使う必要があるようだ。 (エラーとしては temporary value dropped while borrowed creates a temporary which is freed while still in use) clone()して所有権ごと渡してしまえば寿命とかも渡した先でよろしくやってくれそうな気がしていたが、そういうものでもないらしい。(to_owned()とかじゃダメだったしそういう使いかたじゃないのかもしれない)

(非同期実行の終了タイミングは実行までわからないから解放タイミングが把握できないやつ)

(テスト実行では問題にならないのだがapp -> cache or repository とtraitわたしていく時にそれぞれのライフタイムが問題になって、ライフタイムを付けないといけなくなるとフレームワーク(grpcが自動生成するtrait)の要求する形にならないためビルドできないという感じ)

追記2 #
大本のrequestを借用している状態で受け渡していると途中でその一部分のmoveはできないというのがあったがそれは注意不足であった。
問題ない場合はmoveならmoveで切り売りしていく形にしていくというのをちゃんと気をつける必要があった。
